The providers' computer-use tools are action schemas plus a loop you run. The model emits actions; **your** code executes them in a sandbox and sends back a screenshot. M3 has adapters from both providers' payload shapes to one vendor-neutral `Action`; M15's `gui_agents.Action` is the same idea with element-ID actions added.

| | Anthropic | OpenAI |
|---|---|---|
| Tool | `computer_toolset_20260801` (stable, client-executed, 17 member tools such as `screenshot`, `left_click`, `type`, `zoom`; batched actions), plus `browser_toolset_20260801` | Responses API `tools: [{type: "computer"}]` |
| Model output | tool-use blocks with member-tool calls | `computer_call` items with ordered `actions` (`click`, `double_click`, `drag`, `move`, `scroll`, `keypress`, `type`, `wait`, `screenshot`) |
| You return | tool results with screenshots | `computer_call_output` with a screenshot |
| Extras | — | a code-execution approach (Playwright/PyAutoGUI) recommended for the newest model; SDK `ComputerToolset`/`BrowserToolset` helpers with `before_action`/`confirm` hooks |

<Aside type="caution" title="Untested here">
No provider API was called. The adapters in M3 are tested against recorded payload *shapes*; the M15 loop runs on scripted policies. The `before_action`/`confirm` hooks map onto the M15 `Guard.check` step.
</Aside>

## The web: Playwright first

Playwright (1.65.2, Chromium 159) is the executor in M15. What the example uses:

- `page.screenshot()` for pixel observations, `page.evaluate(...)` to collect interactive elements and draw set-of-marks labels;
- `page.mouse.click(x, y)` for coordinate actions, `locator.fill/click` for element actions, with short timeouts so a bad action is an *invalid action*, not a hang;
- `page.route("**/*", …)` as an egress allowlist; a new browser context per episode as a fresh profile.

**browser-use** (1.0.6) wraps an LLM + browser agent; **Playwright MCP** (`@playwright/mcp` 0.0.85) exposes browser actions as MCP tools, mostly over accessibility snapshots. Both are compared, not depended on: no browser-use agent was run for this course.

### browser-use 1.0.4 → 1.0.6: three small lessons in one week

Three patch releases (13–16 Nov 2026) each make a point from earlier modules.

- **1.0.6 changed the default model, and with it your bill (cost, M6).** `Agent(task)` and `ChatBrowserUse()` with no model now run `bu-4.0` instead of `bu-fast`. Its tokens cost 15 times as much ($1.80 / $9.00 per 1M input / output tokens, against $0.12 / $0.60), and it runs at high instead of medium reasoning; the release notes' short test task went from $0.0014 to $0.022. **Always pass `llm=` yourself** (`llm='bu-fast'` keeps the old model and price; `'bu-4.0-mini'` is the cheapest BU 4.0). A default is part of a library's behaviour that can change in a patch release, so the example's `explicit_llm` refuses `None`.
- **1.0.5 judges every run (evals: M6 and the M15 mini-benchmark).** After each run, one more low-effort request to *your* model fills `result.judgement` with `success`, `failure_reason`, `description`, `prompt_injection_detected`, `bot_block_or_captcha_detected` and `gotchas` (at most five lessons, written even on a successful run when the site pushed back). `judge_context=` gives it your criteria; `judge=False` turns it off; its tokens are counted in `result.usage` and `result.cost_usd`. The judge is a model grading its own run, so `judgement_to_eval` treats it as **one signal**: a deterministic, state-based check (as in M15's mini-benchmark) wins when both exist, a CAPTCHA or bot block is labelled an *environment* failure rather than a policy failure, and a detected prompt injection goes to a human whatever the verdict.
- **1.0.4 stopped breaking the prompt cache (cost).** The agent used to drop old screenshots on every new one; each drop rewrote an earlier message, so the provider's prompt cache missed on almost every step (one 705-step task read 27.8M input tokens, only 1.6M from cache). Now screenshots pile up until 20 tool results carry one, then all but the newest 2 lose theirs in one batch. On browser-use's BU Bench v2.1 (200 tasks) the score stayed the same (76.1 vs 76.0) while model cost per task fell from $0.434 to $0.208. `prompt_cost` is a toy model of the same effect: batching **sends more tokens but pays for fewer**, because most of each request is read from cache.

## Sandboxes

Run GUI agents in something you can throw away: a Docker container with Xvfb and a browser, E2B Desktop (`e2b-desktop` 2.7.2), or trycua/cua (`cua-agent` 0.9.1). The course's sandbox is a local app on 127.0.0.1 plus Playwright routing; a Docker image with no outbound network (planned as `envs/cua-web`) is not built yet.

## C++/Rust notes
- If you write your own executor, CDP (Chrome DevTools Protocol) over a WebSocket is the layer Playwright uses for Chromium; a Rust client can drive `Input.dispatchMouseEvent` and `Page.captureScreenshot` directly.
