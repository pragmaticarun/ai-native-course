**After:** M3–M6, M10–M11 · **Suggested time:** ~10 hours · **Code:** [`projects/p1`](https://github.com/pragmaticarun/ai-native-course/tree/main/projects/p1)

Build a coding agent that takes an issue, plans, edits files with read/search/edit tools in a git worktree, runs the tests, iterates, and opens a pull request with a summary and a test report, or escalates when it can't fix the bug.

<Aside type="note" title="Everything is local">
The repo is a git clone of a small library (`textkit`), the remote is a bare git repo in a temp directory, and the "forge" that takes PRs is a JSON file. **No GitHub repo is created or touched**, and the model is scripted (no API key). Running it against a real GitHub sandbox repo is a stretch goal that needs the repo owner's go-ahead.
</Aside>

## M2 · Guardrails in the tools, not the prompt

- paths stay inside the worktree (no absolute paths, `..` or symlink escapes), `.git` is invisible;
- **tests are read-only**: they're the oracle, and an agent that edits them to go green hasn't fixed anything;
- `run_tests` takes only test node ids (no pytest options), with a scrubbed environment, a timeout, host plugins disabled, and a `sitecustomize` that makes socket use fail;
- every result is truncated and counted.

<Aside type="caution" title="A guard, not a sandbox">
The socket patch catches accidents in Python code. Real isolation for untrusted code is a container or a network namespace, which this project doesn't set up (*untested here*).
</Aside>

## M3 · The scripted model

It drives the same tools an LLM would, one call at a time, and sees only tool output. Repair is **mutation search**: flip a comparison, swap `+`/`-`, `and`/`or`, `min`/`max`, `True`/`False`, drop a stray ±1, and keep an edit only if the failing tests pass and then the whole suite passes. Anything that needs new logic is escalated. That's classic search-based program repair: deterministic, testable, and honest about its limits.

## M4 · The loop: budgets and a verified finish

"finish" is a claim. The loop re-runs the full suite itself and checks that the diff is non-empty and inside `src/` before it calls the issue resolved. A model that deletes an assertion and says "all good" gets `finish rejected` (there's an eval for exactly that).

## M5 · The pull request

Commit only `src/`, push the branch to the local origin, and open the PR with the plan, the one-line change, a before/after test report **measured by the loop**, the diff stat and the cost. Escalations open no PR.

## C++/Rust notes
- For a C++ or Rust repo, "run the tests" becomes `ctest` or `cargo test`, and the same rules apply: no flags from the model, a timeout, and a separate target dir per worktree (`CARGO_TARGET_DIR`), or parallel agents serialize on the build lock.
- Mutation operators are language-agnostic. Tools like `cargo-mutants` (Rust) and Mull (C/C++) do the reverse of this agent's search: they mutate to test the tests, which is a good way to check that a benchmark's tests would catch a wrong fix.
- Compile errors are cheap signals: check that a candidate edit compiles (`cargo check`) before spending a test run, as the scripted model does with `ast.parse`.

## Untested and not built
- **No LLM**: the Pydantic AI, Claude Agent SDK and AI SDK (TypeScript) variants from the syllabus are not built; the `Model` protocol is where they'd plug in.
- **No GitHub**: PRs go to a local JSON forge. The GitHub Actions background-agent stretch is not built and needs a sandbox repo the owner creates.
- **No container or network namespace** around test runs (the socket guard is in-process).
