```
user turn ─▶ [Koog graph] LLM ─(tool calls)─▶ tools ─▶ LLM … ─(text)─▶ reply
                              delete_* / share_* ─▶ save PendingAction ─▶ ask the user ─▶ run or decline
                              summarise_notes ─▶ PrivacyRouter ─▶ on-device summariser | cloud (opt-in)
             every step ─▶ SessionStore (history, tool trace, pending approval) ─▶ survives process death
```

<Aside type="caution" title="Built and tested on the JVM and as Android host tests; not run on a phone">
The Android SDK was installed with the owner's approval and CI now builds the app. Everything below was run on the JVM and as Android **host** tests (the same `commonTest` suite on the Android library). The instrumentation tests are **compiled but have not run on a device or emulator**, and the LiteRT-LM backend has **never loaded a model**. In CI the "model" is `FakeLocalModel`, a deterministic rule-based tool router: it tests the agent plumbing, not model quality.
</Aside>

## The kit

A notes store (with a `Persist` hook: memory in tests, a file in `filesDir` on Android), the six tools as Koog `SimpleTool`s, sessions, and 20 golden prompts with the expected tool trajectory and a state check, including paraphrases ("jot down", "remove", "send … to"), two-step requests joined by "then", a denied delete, a denied share, and prompts that should call no tool.

<Snippet path="projects/p6/common/src/commonMain/kotlin/course/fieldnotes/Golden.kt" lang="kotlin" />

`FakeLocalModel` subclasses Koog's `PromptExecutor` and returns real `Message.Assistant` tool calls, so Koog runs the actual graph and tools. A weaker `KEYWORD` mode (literal verbs, one step) is the baseline that shows the metric can tell routers apart.

## M1 · Graph and tools

One Koog agent run per user turn, using a graph strategy built with `strategy { }`, `nodeLLMRequest`, `nodeExecuteTools` and `nodeLLMSendToolResults`, and `onToolCalls` / `onTextMessage` edges. Every tool is wrapped so its call lands in the session's tool trace.

## M2 · Human approval on delete and share

The wrapper saves a `PendingAction`, suspends on `ApprovalGate` (a dialog in the app, a scripted answer in tests), clears it and runs the tool only on "yes". On "no" the model gets "the user declined …" back.

## M3 · Privacy router

The cloud is opt-in and only for long summaries. Private notes, emails and phone numbers, offline use, and short text all stay on the device. The app ships with no cloud configured and no `INTERNET` permission (a unit test checks the manifest).

<Solution path="projects/p6/solution/src/commonMain/kotlin/course/fieldnotes/PrivacyRouter.kt" lang="kotlin" label="Show the router" />

## M4 · Persistence and process death

The ViewModel keeps the agent across configuration changes, and the session file covers process death. The test starts a delete, cancels the coroutine while the approval is pending (the "process dies"), builds a fresh agent from the same stores, and checks that the dialog comes back, the delete runs once, and nothing ran before approval.

## M5 · Android

`androidMain` builds a Koog `MultiLLMPromptExecutor` over `LiteRTLLMClient` with `LiteRTLLModels.FunctionGemma` (FunctionGemma 270M, mobile actions) on `Backend.CPU()`. GPU is a flag that stays off until it passes on the Galaxy A73. The Compose app falls back to the fake router, and says so on screen, when no model file is present.

## C++/Rust notes

- `commonMain` + `expect`/platform source sets is the same split as a portable core plus `#ifdef` or `cfg(target_os)` backends, but checked by the compiler on every target.
- The approval wrapper is a decorator over a trait object: same descriptor, extra policy, one place to audit.
- Persisting the pending action before blocking is write-ahead logging: record the intent, then wait, so recovery can replay or drop it.

## Untested and not built

- **Not run on any device or emulator:** the Compose UI tests, the golden suite on LiteRT-LM, and the offline (airplane-mode) check. No TTFT, tokens/s or Perfetto energy numbers. The A73 self-hosted runner job (`device-lab.yml`) doesn't exist yet.
- The LiteRT-LM backend has never loaded a model file; the GPU option is untested.
- Not built: ML Kit GenAI speech recognition for voice memos (voice memos are notes with a flag), the Gemma 3 1B / Gemma 4 E2B answer model (only referenced), a cloud summariser (the interface and router are there; the app configures none), the Gemini Nano / AppFunctions / Firebase AI Logic flavour, the llama.cpp JNI stretch, and the ORT QNN NPU stretch.
- The Kotlin starter and solution use a Gradle property (`-Pp6.variant`), not `PROJECT_VARIANT`; `check_exercises.py` doesn't cover P6, and the CI `kmp` job checks it instead.
