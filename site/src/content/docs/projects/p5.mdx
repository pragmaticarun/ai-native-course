## The legacy repo

`common/legacy_repo/` ("Larkspur Clips", fictional): `py/clipsvc`, `web/src/format.ts`, `rust/clipcore`. Traps a newcomer (or an agent) falls into:

- the README says `make test`, and there's no Makefile;
- one Python test file, covering one function, with a two-second "staging" test;
- no TypeScript tests at all;
- the Rust tests start with `#![cfg(feature = "full")]`, so `cargo test` is green with none of them run.

Ten seeded tasks (`common/tasks.json`) each break one function; the agent tries candidate fixes (usually a plausible wrong one first) and keeps the first its check accepts. Hidden acceptance tests decide.

## M4 · Before and after

Measured on the course box:

| metric | before | after |
|---|---|---|
| agent task success (10 seeded tasks) | 30% | 100% |
| rework (passed its own check, failed acceptance) | 70% | 0% |
| verify command documented | no (guessed `pytest`) | yes (`./verify.sh`) |
| verify runs by the agent | 11 | 18 |
| review time per PR (course proxy) | 15.0 min | 5.0 min |
| by language: Python / TypeScript / Rust | 2/4 · 0/3 · 1/3 | 4/4 · 3/3 · 3/3 |
| one clean verify run | ~2.2 s (sleeps) | ~0.5–1 s |

Before, the guessed `pytest` only ran one Python file, so seven wrong fixes "passed": that's the 70% rework. The agent runs its check *more* afterwards because the tests reject wrong candidates. Review time is a stated proxy (base + per line + 10 minutes when there's no passing check to trust), not a measurement of people.

## C++/Rust notes

- The Rust trap (`#![cfg(feature = "full")]` on the test file) is common in real crates: CI must run the same feature set the tests need, or `cargo test` reports success with nothing run. `cargo test --all-features` or an explicit list in `verify.sh` is the fix.
- Separate build directories per repo copy: cargo trusts file timestamps, and copying sources with preserved mtimes into a shared `CARGO_TARGET_DIR` gave stale builds during development. The kit copies without metadata and uses one target dir per copy.
- For a C++ component the same steps apply: one documented build-and-test command (CMake presets + `ctest`), tests that run without network, and a fast default suite.
