M3 built a computer-use loop where the model did everything. Here the same job (fill a form, then submit) is an explicit graph:

```
observe ─▶ plan ─▶ guard ─▶ act ─▶ verify ─▶ observe … ─▶ done
                     │ interrupt for consequential actions       └─▶ recover (state didn't change as expected)
```

- **observe**: screenshot + accessibility tree from the (simulated) emulator.
- **plan**: picks the next action and records what the state *should* look like afterwards (`expect`).
- **guard**: reuses M5's risk classifier and untrusted-text flags. A consequential action (here: tapping *Submit*) triggers `interrupt(...)`; injected-looking screen text is flagged.
- **act**: runs the action with a `RetryPolicy` (transient emulator errors are retried).
- **verify**: diffs the new state against `expect`; a mismatch goes to **recover** (re-observe and re-plan) instead of blindly continuing.
- The checkpointer saves every step, so a crashed run resumes with `invoke(None, cfg)`.

The test run: the emulator **crashes at action 4**, `get_state(cfg).next` is `('act',)`, the resumed run continues from there, pauses before *Submit*, is approved, and finishes with 6 steps, 1 recovery, 6 actions and 8 attempts (retries included).
