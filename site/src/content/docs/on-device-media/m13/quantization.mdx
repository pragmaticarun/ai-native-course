## Three things you can quantize

- **Weights:** the file size and most of the memory. GGUF types like `Q8_0` (8-bit, one scale per block of 32), `Q4_0` (4-bit, one scale per block) and `Q4_K_M` (k-quants: super-blocks with per-block scales, mixed precision across tensors).
- **Activations:** matter for integer-only accelerators (NPUs/HTP need quantized activations too).
- **KV cache:** grows with context × layers × KV heads × head dim. Weight quantization doesn't touch it; a KV cache type (`-ctk/-ctv` in llama.cpp), fewer KV heads (GQA/MQA) or a shorter context does.

## Measured: llama.cpp on stories15M

<Snippet path="examples/python/m13/llama_quant.py" />

Run on the course box (x86 "Intel Xeon Processor", 4 threads) on 17 Nov 2026, llama.cpp **b12428** (a post-v1.0.0 build; its tools report `version: 1.0.0-dev (build 12428)`), `stories15M.gguf` F32, 128-token context, our own 1,000-word eval text:

| quant | size MB | PPL | PPL/F32 | mean KLD | same top-1 % | prompt t/s | gen t/s |
|---|---|---|---|---|---|---|---|
| F32 | 98.4 | 5.282 | 1.0 | 0.0 | 100.0 | 13444.2 | 1352.9 |
| Q8_0 | 26.7 | 5.289 | 1.0014 | 0.0011 | 97.4 | 35872.2 | 3610.7 |
| Q4_K_M | 21.0 | 5.429 | 1.0279 | 0.0269 | 90.7 | 17956.7 | 3071.7 |
| Q4_0 | 19.1 | 5.939 | 1.1243 | 0.1114 | 83.3 | 37984.4 | 4154.0 |

The first version of this table (14 Nov 2026) used **b12359**, the v1.0.0 build. Re-running b12359 on the same box straight after the table above gave the same sizes and the same F32, Q8_0 and Q4_K_M quality numbers, and Q4_0 at PPL 5.944 / KLD 0.1115 / 83.3% (5.939 / 0.1114 / 83.3% on b12428), so the bump changed no quality number beyond run-to-run noise. Its speeds were lower in that run (e.g. Q8_0 prompt 23,513 t/s, generation 2,674 t/s), but speeds on a shared box vary between runs, so don't read the difference as a b12428 speed-up.

What to take from it (and what not to):

- **KL divergence and "same top-1" are better quality signals than perplexity alone**: they compare each token's distribution against the F32 model's (`--kl-divergence-base`, then `--kl-divergence`).
- Q8_0 was nearly lossless here; Q4_0 lost noticeably (17% of next-token picks changed); Q4_K_M sat between them.
- **Q4_K_M was slower than Q4_0 and Q8_0 on this CPU and model.** Speed depends on kernels and hardware; don't assume.
- Repeated runs moved some numbers (Q4_0 PPL has been 5.94 in some runs, 6.02 in another). Treat the last digits as noise and check tasks, not just perplexity.
- A real finding: `-ctk q8_0` (quantized KV cache) **failed on this model** (on both b12359 and b12428): "K cache type q8_0 with block size 32 does not divide n_embd_head_k=48". Quantized KV caches need a head dimension divisible by the block size.
- These are x86 numbers on a toy model. **No A73 numbers** until measured on the phone (*untested*).

The CI `llamacpp` job downloads the same release and model and re-runs this table on every push (assertions check ordering, not exact values).

## ONNX Runtime int8 (host half of the NPU stretch)

<Snippet path="examples/python/m13/onnx_quant.py" />

A 64→256→3 MLP trained with numpy and written with `onnx.helper`; `quantize_dynamic` (int8 weights) shrank it from 68.2 KB to 19.0 KB on the box with the same test accuracy (0.996) and full agreement with FP32. The **ORT QNN EP on the A73's Hexagon HTP** (HTP V68, compile the context on the device) is the "may not work" stretch, and it is *untested*.

<Aside type="caution" title="ONNX Runtime's GitHub repo is offline (since 17–18 Nov 2026)">
Since about 22:20 UTC on 17 Nov 2026 (03:50 IST on 18 Nov), ONNX Runtime's GitHub repository has returned **404**: code, issues, the API and every release download. At least seven related repos went with it, including ONNX Runtime GenAI. Microsoft said only: "We have made some repositories private while we investigate malicious content." That came the same evening as the [agent-framework PyPI compromise (M12 L12.3)](/ai-native-course/ai-native/m12/governance/). Nobody has reported ONNX Runtime itself as compromised, and Microsoft hasn't linked the two.

What this means for the course (checked 24 Nov 2026):
- **Install only from the official registries:** PyPI `onnxruntime` 1.32.0 and `onnxruntime-genai` 0.20.0, Maven Central `com.microsoft.onnxruntime:onnxruntime-android` 1.32.0, npm `onnxruntime-node` / `onnxruntime-web` 1.31.1. CI installs from PyPI through `uv.lock` with hashes, so it's unaffected.
- **Expect GitHub source builds and release-asset downloads to fail for now.** That includes scripts that `curl` an ORT tarball from GitHub Releases. Tokenstrom reports that `onnxruntime-node`'s Linux postinstall step, which fetches CUDA files from GitHub, is one of them.
- **Don't switch to a mirror or a "re-upload" of the binaries.** Their origin is hard to verify, and Tokenstrom found some aren't byte-identical (one macOS library differed by 304,583 bytes), so your old checksums no longer match. A hash mismatch is the signal to stop, not something to paper over. Wait for the official source, or vendor a copy you already hashed.

We don't link the repository while it's private. Sources: [Hacker News thread](https://news.ycombinator.com/item?id=50539610) · [Tokenstrom analysis, 18 Nov 2026](https://tokenstrom.com/posts/onnx-runtime-vanishes-from-github-what-breaks-what-works-and-why-mirro/) · [The Hacker News update, 20 Nov 2026](https://thehackernews.com/2026/11/attackers-compromise-microsofts-agent.html)

## Accelerators, using the A73 as the example

| Path | A73 (SM7325) |
|---|---|
| LiteRT NPU (Qualcomm AI Engine Direct) | not supported (list: SM8450 → SM8850) |
| ExecuTorch Qualcomm backend | not supported (SM7325 isn't in `QcomChipset`) |
| ORT QNN EP (HTP) | possible, not verified (ORT documents SM8350, also HTP V68) |
| llama.cpp OpenCL (Adreno) | Adreno 642L not on the verified list |
| CPU (XNNPACK / NEON) | the safe path |

LiteRT `CompiledModel` NPU paths (Qualcomm, MediaTek NeuroPilot, Google Tensor AOT) and Google Play for On-device AI delivery are covered conceptually. `torchao` / LiteRT Torch export are not run here.

<Aside type="tip">
Read vendor tables by chip ID (SM7325), not marketing name, and check the date you read them.
</Aside>

## C++/Rust notes
- `llama-quantize` takes `--imatrix` (importance matrix) to protect the weights that matter most at low bit widths; it's worth trying before you give up on Q4 for a task.
- Memory-mapped GGUF weights + page cache: on Android, a model that "fits" can still get paged out under memory pressure; measure peak RSS and first-token time after the app has been backgrounded.
